Detailed Developer Guide

Architecture, local setup, data model, workflows, security, testing, and deployment for the Stockora PHP/MySQL application.

Version 1.0 · July 2026 · No images included

1. System overview

Stockora is a server-rendered multi-shop POS application. It uses plain PHP with PDO, MySQL/MariaDB, Bootstrap 5, Bootstrap Icons, Chart.js, and project CSS/JavaScript. There is no Composer, Node.js, or asset build process in the current codebase.

Request model: Browser → PHP page/API → shared authorization/helper functions → PDO prepared statement → MySQL. Shop pages scope every operational query to the authenticated shop ID.

2. Local installation and configuration

Requirements

  • PHP with PDO MySQL enabled (XAMPP is supported).
  • MySQL or MariaDB.
  • Apache or another PHP-compatible web server.
  • A writable assets/uploads/ directory when upload features are used.

Installation workflow

  1. Place the repository in the web root, for example C:\xampp\htdocs\stockora.
  2. Create the database: CREATE DATABASE stockora CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
  3. Import database.sql into that database.
  4. Open includes/config.php and set DB host, port, database, user, password, and BASE_URL.
  5. Start Apache and MySQL. Browse to the configured BASE_URL.
  6. Optionally run php seed.php from the project root to create sample data.
  7. Sign in with the seeded administrator only for local verification, then change/remove demo credentials before real deployment.
# Optional development checks php -l admin/invoice_generator.php php -l shop/pos.php php seed.php
Production configuration: do not retain the included root/no-password example database setup. Set a strong database user, correct BASE_URL, HTTPS, production error settings, and safe directory permissions.

3. Authentication, roles, and subscription gates

Shared session and guard logic is in includes/functions.php. Call guards before producing page output.

FunctionPurpose
startSession()Sets HTTP-only, Lax SameSite session-cookie parameters and starts the session.
requireAdmin()Redirects unauthenticated users to the admin login route.
requireShop()Requires shop identity and blocks normal shop pages when subscription is expired/missing.
getSubscriptionStatus()Returns active, expired, or no_subscription based on active rows and end date.
isFreeTrial() / hasPremiumFeatureAccess()Separates core/free-trial access from paid premium access.
requirePremiumFeature()Performs server-side premium access enforcement and redirects to Subscription.

New shop page pattern

<?php require_once '../includes/functions.php'; requireShop(); $shopId = (int) $_SESSION['shop_id']; $db = getDB(); $stmt = $db->prepare('SELECT * FROM products WHERE shop_id = ?'); $stmt->execute([$shopId]); $rows = $stmt->fetchAll(); require_once '../includes/shop_layout.php'; shopHeader('Page title', 'menu_key');

For premium-only shop modules, call requirePremiumFeature($shopId, 'Feature Name') immediately after requireShop(). Do not use navigation hiding as the only control.

Critical workflow integrity

  1. Purchase: create purchase/invoice → increase product stock → write purchase stock movement → record supplier payable/payment accurately.
  2. Sale: validate product belongs to current shop and has stock → insert sale → insert sale items → reduce stock → write sale movement → update customer credit only if required.
  3. Return: validate original sale/item/quantity → insert return/item rows → restore or account for stock → write return movement → adjust refund/credit consistently.
  4. Subscription: record subscription dates/status → record payment with matching subscription when paid → generate invoice only from the completed payment.
Use a database transaction for multi-table changes. If any validation, insert, or stock update fails, roll back so a partial sale/purchase does not corrupt inventory.

5. Coding conventions and safe changes

Database access

  • Use getDB(); it provides a singleton PDO configured for exceptions, associative fetches, and native prepared statements.
  • Use prepared statements for dynamic values. Never concatenate user input into SQL.
  • Scope shop data with WHERE shop_id = ?, using the authenticated session value—not a query-string shop ID.
  • Use safeInt() and safeFloat() only for typed input; also validate business rules, ownership, ranges, fields, and allowed values.

Output and redirects

  • Escape HTML output with htmlspecialchars(..., ENT_QUOTES, 'UTF-8') or the project helper sanitize().
  • Use BASE_URL for internal links and redirects to keep subfolder installations working.
  • Redirect before emitting HTML and follow header(...) with exit;.
  • Keep layout calls consistent: shopHeader() / adminHeader() and their matching footer flow.

Adding a feature

  1. Define actor, data ownership, permissions, subscription requirement, and success/failure states.
  2. Add a reversible migration/schema update. For fresh installs update database.sql; for upgrades add an idempotent migration/check consistent with the project.
  3. Create the page with its guard and shop scoping.
  4. Implement POST handling with server-side validation, prepared statements, CSRF protection, and a transaction if multiple rows change.
  5. Add navigation only after direct-route authorization is enforced.
  6. Test happy path, empty data, unauthorized access, cross-shop IDs, invalid input, duplicate submission, and rollback.

6. APIs, imports, exports, and uploads

The api/ directory contains JSON endpoints such as sales and shop reporting. An API endpoint must authenticate/authorize its caller, set JSON content type, validate parameters, scope queries to the current shop, and return a predictable success/error structure.

header('Content-Type: application/json; charset=utf-8'); // Guard first; validate input; use a prepared, shop-scoped query. echo json_encode(['success' => true, 'data' => $data]); exit;

Import/export safeguards

  • Document an exact import template. Validate headers, required fields, types, price/quantity ranges, duplicates, and category/supplier references.
  • Report row-level errors; do not silently skip invalid business data.
  • Process imports atomically when feasible, or preserve an import log so partial results can be repaired safely.
  • Exports must enforce the same shop/role access as screen data. Log exports where expected and never expose a filesystem path.

Upload safeguards

  • Store uploads in assets/uploads/, not executable source directories.
  • Validate server-side MIME, extension, maximum size, and image content where relevant; generate a server-side file name.
  • Never trust file names/MIME from the browser. Disable PHP execution in the upload directory at web-server level.

Release checklist

  1. Back up database and uploaded assets; confirm restore procedure.
  2. Run PHP syntax checks for changed files, then test with a fresh database or safe staging copy.
  3. Test affected roles and subscription states: active, free trial, expired, and no subscription.
  4. Test sale, purchase, credit payment, return, payment, and invoice flows with expected stock/balance totals.
  5. Set production credentials, BASE_URL, HTTPS, error settings, and web-server permissions.
  6. Import schema/migrations, deploy files, and perform smoke tests.
  7. Monitor PHP/web-server logs, database health, platform health, expiry alerts, and backup jobs after release.
